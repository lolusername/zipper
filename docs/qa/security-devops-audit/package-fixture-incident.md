# Packaging fixture incident — 2026-09-07

The first packaging regression run used a copied `/bin/sleep` executable inside a disposable `Zipper.app` fixture to exercise the running-process guard. Its parent directory was created with `mktemp` under the macOS temporary directory and included `zipper-package-tests.<random>/fixture repo/build/Zipper.app/Contents/MacOS/Zipper`. The random directory name was not captured in the retained output and was subsequently cleaned up.

macOS killed that copied executable with SIGKILL. The test consequently reported that the running-application case had unexpectedly succeeded because the fixture process was already dead. During this work the user reported a macOS alert saying “Zipper.app is damaged and can't be opened.” The fixture launch is a plausible explanation, but the alert's exact target path was not independently verified. No Gatekeeper or quarantine setting was bypassed or changed.

The harness was changed to compile its own small Swift process fixture. A subsequent complete run passed the packaging failure and process-guard scenarios; its output is in [package-tests.txt](package-tests.txt). Every packaging invocation in these tests targeted the temporary copied repository. The actual repository's `build/Zipper.app` and the user's media were not replaced, launched, signed, or modified by these tests. Process inspection after the runs found no remaining packaging fixture processes.

The final fixture preparation now creates a valid bundle with the distinct display name **Zipper Packaging Test Fixture** and identifier `studio.zipper.packaging-test-fixture`, then signs and strictly verifies it with absolute `/usr/bin/codesign` before installing any tool stubs. That final fixture-only adjustment passed shell syntax checking. It has not been relaunched or rerun following the user's alert. The retained passing log predates this final bundle-signing adjustment.

The production packaging fix is separate: it builds, creates icons, signs, and verifies a staged application before an atomic bundle replacement; failures before publication preserve the previous app. It checks the target executable's process path before release compilation and immediately before publication. Those are point-in-time checks, not an OS-level prohibition on someone launching the app during a build. Operators should keep Zipper closed while packaging it. The script fails rather than falling back to a non-atomic replacement when the filesystem cannot perform the requested atomic rename.
